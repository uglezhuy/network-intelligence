## 1. Назначение решения

**Network Intelligence** — чат-бот в мессенджере **MAX**, который за секунды собирает полный цифровой «паспорт» любого сайта, домена или IP-адреса и берёт его под постоянное наблюдение с уведомлениями об изменениях прямо в чат.

Один сервис отвечает на четыре вопроса, которые предприниматель или администратор задаёт про любой сетевой ресурс:

- 🔎 **Что это за ресурс?** — DNS-записи (A/AAAA/MX/NS), HTTP-статус и заголовки, TLS-сертификат (срок действия, протокол), открытые порты.
- 🧭 **Где он находится?** — геолокация по IP: страна, город, координаты, часовой пояс (локальная база, без внешних запросов и ключей).
- 📡 **Всё ли с ним в порядке?** — мониторинг по расписанию: доступность, время ответа, смена IP или DNS, срок жизни сертификата.
- 🛎 **Что изменилось?** — сравнение соседних проверок: изменения записываются в события и приходят уведомлением в MAX / Telegram.

Решение реализовано в формате **чат-бота в MAX** (основной проверяемый канал кейса) с расширением через **Web-версию** (кнопка из чата), **уведомлениями** и дополнительными каналами: Telegram-бот и HTTP API.

## 2. Проблема и ценность для бизнеса

### Кто пользователь

Целевая аудитория — **предприниматели и специалисты, чей доход зависит от работы сайта, интернет-магазина, CRM или сервера**: владельцы малого и среднего бизнеса, веб-мастера и фрилансеры, администраторы и ИТ-подрядчики, обслуживающие чужие проекты.

### Какая проблема решается

- Сайт или сервер — это «лицо» и канал продаж компании. Недоступность в пиковые часы = потерянные заказы и клиенты; истёкший TLS-сертификат = «сайт не безопасен» и отток посетителей.
- Информация о ресурсе разбросана: у регистратора — DNS, у хостинга — статус сервера, в браузере — сертификат, в сторонних сервисах — геолокация и порты. **Пользователю приходится самому сопоставлять данные из 5–10 сервисов** — это ровно тот барьер, о котором говорит кейс («информация распределена между несколькими источниками», «пользователю необходимо самостоятельно сопоставлять большое количество параметров»).
- Типовые платные мониторинги избыточны, сложны и не объясняют, **что именно** изменилось (сменился IP, упал статус, выросло время ответа, скоро закончится сертификат).

### Ценность решения

| Как было (As Is)                                                                            | Как стало (To Be)                                                           |
| ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Вручную открывать сайт, DNS-консоли, сервисы проверки портов и сертификатов (5–10 действий) | Одной командой `/scan <домен>` в MAX получить полный отчёт за ~10–30 секунд |
| Разовые проверки; изменения замечаются через дни                                            | Мониторинг по расписанию + уведомление в чат об изменении                   |
| Нет истории: непонятно, когда и что сломалось                                               | История результатов и событий в БД, сравнение соседних проверок             |
| Дорогие агрегаторы с избыточным функционалом                                                | Бесплатный бот в привычном мессенджере, понятный сразу                      |

### Ожидаемый эффект (как проверить)

- **Время получения ответа** о состоянии ресурса: с десятков минут ручной проверки до **~10–30 секунд** (время одного `/scan`).
- **Количество ручных действий** сокращается до одной команды; не нужно переключаться между сервисами.
- **Скорость реакции на инцидент**: уведомление об изменении приходит автоматически, а не после жалобы клиента.
- Метрики для пилота: доля проверок, завершённых без переключения между сервисами; среднее время от изменения до уведомления; количество обнаруженных событий (истёкший сертификат, смена IP, падение статуса, рост времени ответа).

## 3. Основной пользовательский сценарий

**Приоритетный сценарий — «Проверить свой сервис и взять его под контроль»** (полностью проходит в MAX):

| Шаг | Действие пользователя                       | Результат                                                                                                                                                      |
| --- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Открыть чат-бота Network Intelligence в MAX | Бот приветствует и показывает старт-гайд (`/help`)                                                                                                             |
| 2   | Отправить `/scan example.com`               | Выполняются 5 анализов; бот присылает отчёт: DNS (A/AAAA/MX/NS), HTTP-статус и время ответа, TLS-сертификат (сколько дней осталось), открытые порты, гео по IP |
| 3   | Отправить `/monitor example.com 5`          | Создан монитор: проверка каждые 5 минут, результаты сохраняются в БД                                                                                           |
| 4   | Через 2+ цикла отправить `/events`          | Бот показывает изменения (статус, время ответа, IP, порты) или «изменений нет»                                                                                 |
| 5   | Отправить `/monitors`                       | Список своих мониторов с ID и статусами                                                                                                                        |
| 6   | Отправить `/stop 1` (или `/stop all`)       | Монитор остановлен (другие продолжают работать)                                                                                                                |
| 7   | Отправить `/app`                            | Бот присылает кнопку «🚀 Открыть Web-версию» — расширенный интерфейс: страницы «Сканирование», «Мониторы», «События», графики истории                          |

**Почему сценарий ценен:** владелец сайта раньше вручную проверял «открывается ли сайт», «не истёк ли сертификат», «не сменился ли IP» в десятке разрозненных сервисов. Теперь это делает один бот в привычном мессенджере — регулярно, автоматически и с уведомлениями об изменениях (дополнительный сценарий проверки см. в [разделе 13](#13-пошаговый-сценарий-проверки)).

## 4. Решение в MAX

MAX — основная среда реализации и взаимодействия (ограничение №2 кейса). Проект использует официальное API платформы MAX:

| Возможность MAX         | Как используется                                                                 | Где в коде                                       |
| ----------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------ |
| Long-polling обновлений | `GET https://platform-api2.max.ru/updates` — бот получает команды пользователя   | `src/maxBot/getTelegramChatIdAndLastUpdateId.ts` |
| Отправка сообщений      | `POST https://platform-api2.max.ru/messages?user_id=<id>` — отчёты и уведомления | `src/maxBot/*`                                   |
| Меню команд бота        | `PATCH https://platform-api2.max.ru/me/commands` — регистрация команд            | `src/maxBot/setMaxCommands.ts`                   |
| Интерактивность         | inline-кнопка «🚀 Открыть Web-версию» в команде `/app`                           | `src/maxBot/processMessage.ts`                   |

### Команды бота (в MAX и Telegram одинаковые)

| Команда                     | Описание                         | Пример                   |
| --------------------------- | -------------------------------- | ------------------------ |
| `/help`                     | Подробная инструкция и примеры   | `/help`                  |
| `/scan <домен или IP>`      | Полный разовый анализ            | `/scan example.com`      |
| `/monitor <домен> <минуты>` | Мониторинг с интервалом          | `/monitor example.com 5` |
| `/events <домен> <минуты>`  | Мониторинг + сравнение изменений | `/events example.com 60` |
| `/monitors`                 | Список своих мониторов           | `/monitors`              |
| `/stop [id или all]`        | Остановить монитор(ы)            | `/stop 2`                |
| `/app`                      | Открыть Web-версию               | `/app`                   |

Работает как в **мобильной**, так и в **веб-версии MAX** (требование кейса №3). Уведомления о событиях мониторинга приходят прямо в чат MAX.

## 6. Запуск решения

### 6.1 Быстрый старт: Docker (все компоненты одной командой)

**Требования:** Docker Desktop / Docker Engine с Compose v2.

```bash
# 1. Скопировать шаблон окружения и вписать свой токен MAX (обязательно)
cp .env.example .env
#    → в .env задать MAX_BOT_TOKEN (токен выдан организаторами хакатона)

# 2. (опционально) скачать гео-базу ipapi.is, чтобы работал IP-анализатор
#    https://ipapi.is/ → Databases → Geolocation Database IPv4
#    → сохранить как data/ipapi/geolocationDatabaseIPv4.csv

# 3. Одна команда запуска всех компонентов
docker compose up --build
```

**Что поднимает команда:** контейнеры MySQL → бэкенд (API + мониторинг + Telegram/MAX-боты) → Web-интерфейс → Mini App. Данные БД сохраняются в volume `mysql-data`, при последующих запусках `docker compose up` пересоздание БД не требуется.

**Ожидаемые адреса после запуска:**

| Сервис        | Адрес                                                                                          |
| ------------- | ---------------------------------------------------------------------------------------------- |
| HTTP API      | http://localhost:3000                                                                          |
| Web-интерфейс | http://localhost:5173                                                                          |
| Mini App      | http://localhost:5174                                                                          |
| MySQL         | внутри сети compose (`db:3306`); наружу порт не публикуется (без конфликтов с локальной MySQL) |

**Проверка:** в логах бэкенда должны появиться строки `API server started: http://localhost:3000`, `MAX bot started`, `Telegram bot started` (и `IP database loaded: N records`, если гео-база смонтирована). Инструкция по прохождению основного сценария — [раздел 13](#13-пошаговый-сценарий-проверки).

> **Внешний сервис, который невозможно воспроизвести внутри Docker:** платформа MAX (`platform-api2.max.ru`). Для работы основного сценария в MAX нужен токен чат-бота, выдаваемый организаторами хакатона; код связывается с платформой только по официальному API и не требует других внешних систем.

### 6.2 Локальный запуск без Docker

**Требования:** Node.js 22+ (используются встроенные модули `node:dns`, `node:tls`, `node:net`, `node:http`, `fetch`) и работающий MySQL (по умолчанию `localhost:8889`, БД `network_intelligence`, `root/root`; настраивается переменными окружения).

```bash
# Бэкенд (корень репозитория)
npm ci                 # установка зависимостей по package-lock.json
npm run build          # компиляция TypeScript → dist/
npm start              # API + мониторинг + Telegram-бот + MAX-бот

# Веб-интерфейс (отдельный терминал)
cd web-app
npm ci
npm run dev            # http://localhost:5173

# Mini App (отдельный терминал, в разработке)
cd mini-app
npm ci
npm run dev            # http://localhost:5174

# CLI-режим (разовое сканирование, без сервера)
node dist/index.js scan example.com
node dist/index.js monitor example.com 5
node dist/index.js monitor stop all
```

> Web-интерфейс и Mini App обращаются к API через модуль `src/api.ts`: адрес берётся из переменной **`VITE_API_BASE`**, по умолчанию `http://localhost:3000`. Локально менять ничего не нужно. **Переключение «локально ⇄ сервер» без правок кода:** на VPS достаточно задать `VITE_API_BASE=https://api.megafonhome.ru` (в `.env` сервера) — это же значение подхватится контейнерами web-app и mini-app из `VITE_API_BASE_WEB` / `VITE_API_BASE_MINI`.

### 6.3 База данных

- В Docker схема создаётся автоматически при первом старте MySQL из `database/init.sql`.
- При локальном запуске выполните `database/init.sql` вручную (например: `mysql -u root -p network_intelligence < database/init.sql`) или в любом MySQL-клиенте.
- Параметры подключения задаются переменными `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME` (см. [раздел 7](#7-переменные-окружения)); значения по умолчанию соответствуют локальной конфигурации разработки.

### 6.4 Локальная гео-база (ipapi.is)

IP-геолокация работает по **локальной** базе от [ipapi.is](https://ipapi.is/) — в Git она не хранится (файл превышает лимит GitHub в 100 МБ). Прямая ссылка для скачивания (одинаково работает на локальной машине и на VPS):

```bash
# в корне проекта
mkdir -p data/ipapi
curl -L -o /tmp/geo.zip https://ipapi.is/data/geolocationDatabaseIPv4.csv.zip
unzip -o /tmp/geo.zip -d data/ipapi
rm /tmp/geo.zip
```

При запуске в логе появится `IP database loaded: N records` (объём базы растёт: ~200–600 МБ в зависимости от версии). **Если файла нет — IP-анализатор вернёт понятную ошибку, остальные 4 анализатора и весь сценарий продолжат работать.**

### 6.5 Остановка и повторный запуск

| Действие                        | Команда                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------ |
| Остановить все контейнеры       | `docker compose stop`                                                          |
| Остановить и удалить контейнеры | `docker compose down` (данные БД сохраняются в volume)                         |

### 6.6 Развёртывание и обновление на сервере (Git ↔ Docker)

Git и Docker **напрямую не связаны**: GitHub хранит только текст кода, Docker о нём ничего не знает. Связку выполняют команды на сервере (или скрипт [`deploy.sh`](deploy.sh)):

| Шаг | Кто выполняет            | Что происходит                                                                                                                        |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | разработчик (локально)   | `git commit` + `git push` — код уходит на GitHub                                                                                       |
| 2   | администратор на сервере | `git pull` — файлы проекта обновляются в каталоге `/root/network-intelligence`                                                         |
| 3   | Docker (на сервере)      | `docker compose up --build -d` — читает **локальный** `compose.yaml`, собирает образы по `Dockerfile` и запускает 4 контейнера          |
| 4   | контейнер MySQL          | при **первом** старте с пустым volume выполняет `database/init.sql` (7 таблиц). Далее данные живут в volume `mysql-data` и не теряются |

Из интернета Docker скачивает только **базовые образы** (`node:22-slim`, `mysql:8.4`) с Docker Hub — но не код проекта. Код всегда берётся из локальной папки, обновлённой через `git pull`.

**Одна команда для обновления на сервере:**

```bash
cd /root/network-intelligence
./deploy.sh          # git pull → пересборка → ожидание API → проверка сервисов
```

**Что происходит автоматически после запуска:**

- контейнеры с `restart: unless-stopped` поднимаются сами после перезагрузки сервера или падения процесса;
- MAX- и Telegram-боты работают внутри контейнера `api` (длительный цикл long-polling) — отдельно запускать их не нужно;
- nginx и таймер продления сертификатов (certbot) обслуживает системный `systemd`.

**Что выполняется руками:** обновление кода и пересборка (шаги 2–3 выше), а также пересоздание контейнеров после правки `.env`:

```bash
nano .env
docker compose up -d api web-app mini-app    # переменные применяются при СОЗДАНИИ контейнера, а не при restart
```

> Данные БД, сканы, мониторы и события при обновлениях **не теряются**: они находятся в volume `mysql-data`, а не внутри контейнера.

## 11. Описание работы с данными

| Таблица БД                             | Назначение                                                                     | Кто пишет / читает                        |
| -------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------- |
| `scans`                                | Результаты разовых сканирований (JSON-снимок 5 анализов)                       | API, боты → пишут; Web-интерфейс → читает |
| `monitors`                             | Мониторы: цель, интервал, статус, каналы уведомлений TG/MAX                    | боты, Web-интерфейс                       |
| `monitor_results`                      | Результаты каждого цикла мониторинга (JSON)                                    | монитор → пишет; API/графики → читают     |
| `monitor_events`                       | Зафиксированные изменения (параметр, старое/новое значение)                    | `monitor_events.ts` → пишет; Web → читает |
| `telegram_max_web_users`               | Пользователи каналов (Telegram / MAX / web; сейчас — по одной записи на канал) | боты при первой команде                   |

- Схема — `database/init.sql` (в Docker применяется автоматически при первом старте MySQL; идемпотентна, `IF NOT EXISTS`).
- Результаты проверок хранятся как **JSON-документы** (валидный JSON, MySQL 8 `JSON` тип).
- Пользователи ведутся по каналам (поле `platform`); единая сущность «Пользователь» с несколькими каналами — в планах (см. [раздел 16](#16-потенциал-развития-и-масштабирование)).

## 12. Порядок работы с тестовыми данными

1. **Тестовый пользователь:** Web-интерфейс и API используют тестовый `TELEGRAM_CHAT_ID` (по умолчанию `503362430`) вместо авторизации — это **явно модельная часть** (пометки `// тестовый ID` в коде).
2. **Данные проверок — реальные:** `/scan`, `/monitor`, `/events` выполняют живые проверки к указанному домену/IP; для демонстрации подойдут любой рабочий сайт (например `example.com`) и собственный сайт/сервер.
3. **Гео-база:** если `data/ipapi/geolocationDatabaseIPv4.csv` не скачана, блок IP возвращает строку с понятной ошибкой — на остальной сценарий это не влияет.
4. **Токены:** реальные токены хранятся только в локальном `.env` (в `.gitignore`); в репозиторий и в `.env.example` они не попадают.
5. **Сброс данных для чистого демо:** `docker compose down -v` полностью очистит БД; при следующем `up` схема создастся заново.

## 16. Потенциал развития и масштабирование

### Ядро продукта (не меняется при масштабировании)

Основная проблема (контроль цифровых активов бизнеса), логика сценариев бота, архитектура «5 анализаторов → мониторинг → события → уведомления», базовая модель данных и механика взаимодействия в чате.

### Переменная часть (адаптируется под контекст)

Наборы проверок и порогов под отрасль, региональные/отраслевые справочники (например, ИТ-хостинг vs e-commerce vs АПК), роли пользователей (владелец / администратор / подрядчик с несколькими клиентами), интеграции с хостингами, доменными регистраторами и сервисами мониторинга.

### Куда масштабируем дальше (по приоритету)

1. **Полноценная Web-версия** — уже заложено: страницы «Сканирование», «Мониторы», «События», график истории. Дальше: реальная авторизация, отдельные страницы анализа (DNS / HTTP / IP / TLS / Порты) с историей, настройки порогов и интервалов.
2. **Мини-приложение для MAX** — полноценный Mini App внутри MAX через официальные возможности платформы (MAX Bridge, MAX UI): списки, формы настройки монитора, графики — вместо открытия Web-версии в браузере. Это выделит решение на фоне простых ботов (платформенный бонус кейса).
3. **Мини-приложение для Telegram** — есть задел (`mini-app`): нужен стабильный HTTPS-домен, корректный маршрут API и привязка к реальному пользователю.
4. **Алертинг и уведомления** — классификация изменений по критичности, расписание уведомлений, агрегация событий.
5. **Продуктовая упаковка под сегменты** — каталог «проверь свой сайт перед приёмкой» для фрилансеров и агентств; «контроль SLA» для подрядчиков и хостингов; «контрагент-скан» (проверка сайта партнёра перед интеграцией).

### Тиражирование: конкретный сценарий

Первый контекст — **ИТ-подрядчики и веб-студии** (несколько клиентских сайтов на обслуживании). Пилот: студия подключает мониторы клиентов, бот в MAX присылает уведомления о падениях и истечении сертификатов, студия показывает клиенту прозрачный отчёт. Затем — горизонтально на агентства, e-commerce и хостинг-провайдеров (продукт встраивается в их панели управления через API).

**Условия адаптации:** точечная интеграция с хостинг-площадками/регистраторами (SSL, DNS-зоны), авторизация и мультитенантность, региональные копии гео-данных. **Риски:** изменение правил и API платформы MAX, кеширование DNS у провайдеров, чувствительность данных клиентов (нужна политика хранения), зависимость от доступности платформы MAX.

### 17.1 Как проверить зафиксированную версию

Финальная версия исходного кода помечена тегом **`v1.0-final`** — неизменяемой ссылкой в GitHub. Полный commit hash берётся из тега:

```bash
git clone https://github.com/uglezhuy/network-intelligence
cd network-intelligence
git checkout v1.0-final          # ровно тот код, который сдаётся
git rev-parse HEAD               # полный 40-символьный commit hash зафиксированной версии
```

Хеш коммита Git вычисляет из содержимого версии, поэтому изменить сданный код задним числом нельзя: любая правка файлов даёт **другой** хеш и существует только как новый коммит. Полный хеш и дата фиксации продублированы в описании тега на GitHub и в заявке (форме сдачи кейса).

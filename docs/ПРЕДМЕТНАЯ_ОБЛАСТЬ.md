# Предметная область проекта «Network Intelligence»

> Документ описывает предметную область информационной системы **Network Intelligence** —
> сервиса анализа и мониторинга доменов и IP-адресов. Описание содержит назначение системы,
> ключевые сущности, их атрибуты и связи, основные процессы, бизнес-правила и используемые термины.

---

## 1. Назначение системы

**Network Intelligence** — это сервис, который отвечает на вопросы о любом сайте, домене или сервере:

- **Что это за сайт?** — определяются DNS-записи (A/AAAA/MX/NS), HTTP-статус и заголовки,
  данные TLS-сертификата, открытые порты.
- **Где физически находится сервер?** — геолокация по IP-адресу (страна, город, координаты,
  часовой пояс) на основе локальной базы без внешних HTTP-запросов.
- **Всё ли с ним в порядке?** — постоянный мониторинг: сервис по расписанию повторяет анализ
  и сравнивает соседние результаты.
- **Что изменилось?** — при обнаружении изменений сервис записывает **событие** и уведомляет
  пользователя в мессенджеры Telegram и MAX.

Сфера применения: разведка перед подключением к серверу, наблюдение за собственными сервисами,
контроль доступности, отслеживание срока действия TLS-сертификатов и изменений конфигурации.

---

## 2. Общее описание предметной области

Предметная область системы — **администрирование сетевой инфраструктуры и веб-сервисов на
уровне наблюдения (мониторинга) и диагностики**. Система работает с сетевыми ресурсами
(доменами и IP-адресами) как с объектами наблюдения и предоставляет пользователю:

1. **Разовый анализ** («что сейчас с ресурсом») — полный снимок состояния ресурса по 5 видам
   проверок.
2. **Непрерывное наблюдение** («следить за ресурсом») — периодические проверки по заданному
   интервалу и сохранение истории результатов.
3. **Детектирование изменений** («что изменилось со вчера») — сравнение соседних результатов
   и фиксация отклонений в виде событий.
4. **Оповещение** («сообщить об изменении») — доставка уведомлений пользователю в Telegram
   и/или MAX по заранее настроенным каналам.

Отличительная черта области: система **не вмешивается** в работу наблюдаемых ресурсов
(только чтение/проверка), а решает задачу **сбора, хранения и интерпретации** фактов о
состоянии ресурсов.

## 3. Сущности предметной области

### 3.1 Пользователь (User)

Лицо, использующее систему через один из каналов: Telegram-бот, MAX-бот, веб-интерфейс
или Telegram Mini App.

**Атрибуты (таблица `telegram_max_web_users`):**

| Атрибут | Описание |
| --- | --- |
| `id` | Внутренний идентификатор пользователя |
| `telegram_user_id` | Идентификатор пользователя в экосистеме канала (Telegram или MAX) |
| `telegram_chat_id` | Идентификатор чата для доставки сообщений |
| `username` | Имя пользователя в канале |
| `platform` | Канал: `telegram`, `max` или веб |
| `created_at` | Дата регистрации |

*Примечание к предметной области:* сейчас один пользователь может быть представлен несколькими
записями (по одной на канал). В перспективе это должна быть единая сущность с несколькими
каналами доставки.

### 3.2 Цель наблюдения (Target)

Домен или IP-адрес, над которым выполняется анализ и мониторинг. Задаётся пользователем
в виде строки (например, `example.com` или `93.184.216.34`).

### 3.3 Разовое сканирование / Результат анализа (Scan)

Однократный полный анализ цели по 5 анализаторам: DNS, HTTP, IP/геолокация, TLS, порты.
Выполняется по команде пользователя (CLI, бот, веб-страница).

**Атрибуты (таблица `scans`):**

| Атрибут | Описание |
| --- | --- |
| `id` | Идентификатор сканирования |
| `target` | Просматриваемая цель |
| `data` | Результаты всех 5 анализаторов в формате JSON |
| `telegram_user_id` | Пользователь, запустивший сканирование (может отсутствовать для CLI) |
| `created_at` | Дата и время выполнения |

### 3.4 Монитор (Monitor)

Сущность, описывающая **постоянное наблюдение** за целью: что проверяется, как часто,
кому и при каких условиях отправлять уведомления.

**Атрибуты (таблица `monitors`):**

| Атрибут | Описание |
| --- | --- |
| `id` | Идентификатор монитора |
| `target` | Цель наблюдения (домен/IP) |
| `interval_minutes` | Периодичность проверок в минутах |
| `status` | Состояние: `active` / `stopped` |
| `telegram_user_id` | Владелец монитора |
| `type` | Модель мониторинга (доп. признак) |
| `send_monitor_notificationsTG` | Флаг: уведомлять в Telegram о событиях изменений |
| `send_event_notificationsTG` | Флаг: уведомлять в Telegram о результатах цикла |
| `send_monitor_notificationsMAX` | Флаг: уведомлять в MAX о событиях изменений |
| `send_event_notificationsMAX` | Флаг: уведомлять в MAX о результатах цикла |
| `created_at` | Дата создания |

Жизненный цикл: **создан → активен → остановлен/удалён**. Остановка не удаляет историю;
удаление монитора каскадно удаляет его результаты и события.

---
### 3.5 Результат цикла мониторинга (Monitor Result)

Результат одного прохода (цикла) мониторинга: тот же набор данных анализа цели, что и у
разового сканирования, но привязанный к конкретному монитору и точке времени.

**Атрибуты (таблица `monitor_results`):**

| Атрибут | Описание |
| --- | --- |
| `id` | Идентификатор результата |
| `monitor_id` | Монитор, которому принадлежит результат (FK, каскадное удаление) |
| `data` | JSON-результат анализа цели |
| `created_at` | Дата и время выполнения цикла |

История результатов образует **временной ряд**, по которому сравниваются соседние проверки.

### 3.6 Событие изменения (Monitor Event)

Зафиксированный факт отклонения между двумя соседними результатами мониторинга по
конкретному параметру.

**Атрибуты (таблица `monitor_events`):**

| Атрибут | Описание |
| --- | --- |
| `id` | Идентификатор события |
| `monitor_id` | Монитор, на котором обнаружено изменение |
| `parameter` | Изменившийся параметр (например, `http status`, `responseTime`, `dnsInfo ipv4`) |
| `old_value` | Значение параметра в предыдущем результате |
| `new_value` | Значение параметра в новом результате |
| `created_at` | Дата и время обнаружения |

### 3.7 Уведомление и Алерт (Notification / Alert)

**Уведомление** — сообщение, отправляемое пользователю через канал доставки (Telegram или MAX)
при наступлении события изменения или по завершении цикла мониторинга. Настройки доставки
хранятся в мониторе (флаги `send_*notificationsTG/MAX`).

**Алерт** — экстренное предупреждение об изменении (в текущей версии логируется в консоль;
в планах — вывод в канал оповещения).

## 4. Связи между сущностями

```
Пользователь (telegram_max_web_users)
     │  1:N
     ▼
  Монитор (monitors) ──► 1:N ──► Результат мониторинга (monitor_results)
     │ 1:N                             │ сравнение соседних
     ▼                                 ▼
  Событие изменения (monitor_events) ──┘
     │ порождает
     ▼
  Уведомление в Telegram / MAX  (по флагам монитора)

Цель (домен/IP) ── 1:N ──► Разовое сканирование (scans)
```

Ключевые правила связи:

- **Монитор → Результаты**: один монитор имеет множество результатов; при удалении монитора
  его результаты удаляются каскадно (`ON DELETE CASCADE`).
- **Результаты → События**: два соседних результата одного монитора сравниваются; изменение
  значений параметров порождает события.
- **Монитор → Уведомления**: уведомления порождаются событиями (и результатами цикла) и
  отправляются владельцу монитора в выбранные каналы (Telegram и/или MAX), если
  соответствующие флаги включены.
- **Пользователь → Объекты**: пользователю принадлежат мониторы и сканирования; операции
  «остановить мои мониторы», «показать мои мониторы» выполняются по идентификатору
  пользователя.

## 5. Основные процессы (сценарии использования)

### 5.1 Разовое сканирование

1. Пользователь задаёт цель (домен/IP) через CLI, бота или веб-страницу.
2. Система выполняет анализ цели всеми 5 анализаторами (DNS, HTTP, IP/геолокация, TLS, порты).
3. Результат сохраняется в `scans`, выводится пользователю в текстовом/веб-виде.
4. Опционально (в ботах) результат отправляется пользователю обратным сообщением.

### 5.2 Создание мониторинга

1. Пользователь указывает цель, интервал проверок (в минутах) и, в зависимости от канала,
   выбирает, какие уведомления включать (события изменений / результаты цикла, Telegram / MAX).
2. Система создаёт монитор со статусом `active` и сразу запускает первый цикл.
3. Мониторинг работает в фоне: повторяется каждые `interval_minutes`.

### 5.3 Цикл мониторинга (основной процесс)

Каждый цикл:

1. Выполняется анализ цели (тот же, что и при разовом сканировании).
2. Результат сохраняется в `monitor_results`.
3. Сравниваются **два последних** результата монитора по списку контролируемых параметров.
4. Если изменение превышает порог — создаётся запись в `monitor_events` и срабатывает алерт.
5. По настроенным флагам уведомлений события/результаты отправляются владельцу
   в Telegram и/или MAX.
6. Цикл ожидает следующий интервал и повторяется.

### 5.4 Возобновление мониторов при перезапуске сервиса

При старте сервис выбирает все мониторы со статусом `active` и автоматически запускает
их циклы заново (отказоустойчивость: наблюдение продолжается после рестарта).

### 5.5 Управление мониторами

- **Остановка** одного монитора (по id), всех мониторов или «моих мониторов» (по владельцу) —
  статус переводится в `stopped`, цикл прекращается, история сохраняется.
- **Запуск** остановленного монитора — статус возвращается в `active`, мониторинг возобновляется.
- **Удаление** монитора — запись удаляется вместе с историей результатов и событий.

### 5.6 Просмотр данных

- Список мониторов пользователя (боты: `/monitors`; веб: страница «Мониторы»).
- Полная история результатов конкретного монитора (`MonitorFullResultByID`).
- История событий (страница «События», в разработке).

## 7. Правила предметной области (ограничения и допущения)

1. **Цель**: наблюдению подлежат сетевые ресурсы — домены и IP-адреса. Анализ выполняется
   только на чтение и не изменяет состояние ресурса.
2. **Периодичность**: интервал мониторинга задаётся в минутах и должен быть положительным
   числом; проверка с меньшим интервалом повторяется чаще.
3. **Контролируемые параметры и пороги** (заданы в `src/monitor_events.ts`):
   - `responseTime` — изменение более чем на **20 мс**;
   - `bodySize` — изменение более чем на **1000 байт**;
   - IP (IPv4), MX, NS, HTTP-статус, HTTP-сервер, список портов — любое изменение значения.
4. **Событие** формируется только при наличии **как минимум двух** результатов монитора;
   сравнение выполняется между двумя последними.
5. **Уведомления**: для каждого канала (Telegram, MAX) настройки доставки независимы и
   включаются флагами монитора; без включённого флага события/результаты не отправляются.
6. **Доставка уведомлений привязана к владельцу монитора**: получатель определяется по
   идентификатору пользователя, сохранённому при создании монитора.
7. **Жизненный цикл монитора**: остановленный монитор не выполняет циклы, но сохраняет
   историю; повторный запуск переводит его в `active` и возобновляет циклы.
8. **Восстановление после перезапуска**: все мониторы со статусом `active` автоматически
   возобновляются при старте сервиса.
9. **Проверяемые порты**: фиксированный список `21, 22, 25, 53, 80, 443, 8080`.
10. **Геолокация**: определяется по локальной базе (без внешних запросов); при отсутствии
    IP в базе возвращается признак ошибки.
11. **Авторизация**: в текущей версии для веб-интерфейса используется тестовый
    идентификатор пользователя; полноценная авторизация планируется.

## 8. Анализаторы и контролируемые параметры

| Анализатор | Что проверяет | Основные выходные данные |
| --- | --- | --- |
| **DNS** | Записи A, AAAA, MX, NS | IPv4, IPv6, почтовые серверы, NS-серверы |
| **HTTP** | Ответ веб-сервера | Статус, время ответа, заголовки (включая security: HSTS, CSP, X-Frame-Options), title, размер тела |
| **IP / геолокация** | Окружение IP-адреса | Страна, регион, город, координаты, часовой пояс, точность |
| **TLS** | TLS-соединение и сертификат | Протокол (TLS 1.x), valid_from/valid_to, дней до истечения |
| **Порты** | Открытость фиксированного списка портов | Статус: `open` / `closed` / `timeout` |

Каждый анализ возвращает **единый JSON-документ** с результатами всех анализаторов,
который хранится как в `scans`, так и в `monitor_results`.

## 9. Каналы взаимодействия с системой

| Канал | Описание | Основные операции |
| --- | --- | --- |
| **CLI** | Командная строка (`node dist/index.js …`) | `scan <домен>`, `monitor <домен> <минуты>`, `monitor stop <id>/all` |
| **HTTP API** (порт 3000) | REST-подобные эндпоинты для веб-интерфейса | сканирование, список мониторов пользователя, добавление/запуск/остановка/удаление монитора, результаты |
| **Telegram-бот** | Обработка команд в чате | `/scan`, `/monitor`, `/events`, `/stop`, `/monitors`, `/app` |
| **MAX-бот** | Те же команды в мессенджере MAX (платформа `platform-api2.max.ru`) | те же команды |
| **Веб-интерфейс** | Vite + React (SPA) | страницы «Главная», «Сканирование», «Мониторы», «События» |
| **Telegram Mini App** | Web App внутри Telegram | просмотр списка мониторов текущего пользователя |

Уведомления об изменениях доставляются только в **Telegram** и **MAX** — по настройкам
монитора; веб-интерфейс является консолью для запуска проверок и просмотра данных.

## 10. Глоссарий ключевых терминов

| Термин | Определение |
| --- | --- |
| **Цель (Target)** | Домен или IP-адрес, объект анализа и мониторинга |
| **Анализатор** | Модуль, выполняющий один вид проверки (DNS, HTTP, IP, TLS, порты) |
| **Сканирование (Scan)** | Разовое выполнение полного анализа цели |
| **Мониторинг (Monitor)** | Периодически повторяемый анализ цели с сохранением истории |
| **Цикл (итерация) мониторинга** | Один прогон анализа в рамках мониторинга |
| **Событие (Event)** | Зафиксированное изменение контролируемого параметра между соседними циклами |
| **Порог (Threshold)** | Величина отклонения числового параметра, при которой изменение считается событием |
| **Уведомление** | Сообщение пользователю в Telegram/MAX о событии или результате цикла |
| **Алерт** | Экстренное предупреждение об изменении (сейчас логируется в консоль) |
| **Флаги уведомлений** | Настройки монитора, определяющие канал и тип отправляемых уведомлений |
| **Активный / остановленный** | Состояние монитора: выполняется/приостановлен |

## 11. Направления развития (в рамках предметной области)

- Страница «События» — полноценный вывод и фильтрация истории изменений (частично готова).
- Отправка алертов в Telegram/MAX (сейчас — только лог в консоль).
- Отдельные страницы анализа (DNS, HTTP, IP, TLS, Порты) с историей.
- Авторизация пользователей веб-интерфейса и Mini App (сейчас — тестовый идентификатор).
- Единая сущность «Пользователь» с несколькими каналами доставки (сейчас пользователи
  ведутся по каналам).
- Настройки периодичности, порогов и списка портов.
